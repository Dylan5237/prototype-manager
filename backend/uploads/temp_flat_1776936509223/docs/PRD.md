## 1. 背景与目标

### 1.1 背景

天宫开发平台采用**精简版 GitFlow** 进行业务域版本管理：

- **main 分支**：唯一的持续建模分支，所有日常业务编辑与版本发布均在此分支上进行。
- **hotfix/bugfix 分支**：当生产环境出现紧急 BUG 时，从 main 分支的某个历史 Tag 拉出 bugfix 分支进行修复。修复完成后，**必须合并回 main 分支**。

业务域模型以 JSON 文件形式存储（包含实体定义、字段属性、业务流程节点、字典配置等）。由于 JSON 是纯文本，直接使用 Git 原生的文本 Diff 会让业务人员难以阅读，无法快速定位诸如"患者姓名字段长度变更"或"住院医嘱流程节点删除"这类语义化改动。因此，我们需要一套**结构化、可视化、可交互**的合并方案。

### 1.2 目标

为"BUG 修复"列表中的【合并】按钮提供两套完整的合并能力：

1. **交互一（结构化对比）**：按变更类型分类导航，适合快速定位和处理大量分散变更。
2. **交互二（表单三栏对比）**：以实体编辑页为蓝本，左/中/右并排展示 Hotfix / Base / Main，类似 Notepad++ 文本比较插件的直观对比体验，适合细粒度核对单个实体的每一处字段差异。

两套交互共用同一套底层 diff3 算法与裁决结果，用户可随时切换体验。

同时，优化版本发布管理与业务域设计的整体信息架构：
- **版本发布管理**：移除独立的左侧版本列表，将版本切换器下沉到"概览"子页签内，符合"概览按版本看，发布/BUG 全局管理"的直觉。
- **业务域设计**：新增"业务模型切换页签"作为建模子页签的上级，解决原树结构中模型叶子节点被移除后的切换问题。

### 1.3 成功指标

- 业务人员能在 **3 分钟内**定位并处理完一处合并冲突。
- 合并操作导致的模型回滚率 < 1%。
- 用户对合并界面的 NPS 评分 ≥ 7 分。
- 交互二的首次使用上手率（无帮助文档完成一次合并）≥ 80%。

## 2. 术语表

| 术语 | 说明 |
|------|------|
| Base | 合并的共同祖先，即创建 hotfix 时对应的 main Tag 版本。 |
| Main（目标分支） | 当前最新的 main 分支内容。 |
| Hotfix（源分支） | 待合并的 hotfix/bugfix 分支内容。 |
| 语义级 Diff | 基于 JSON 对象树进行字段级、数组元素级比较，识别新增、删除、修改、冲突。 |
| 医疗业务节点 | 实体（Entity）、字段（Field）、业务流程（Process）、字典项（Dictionary）。 |
| Auto 合并 | 仅有一方（Main 或 Hotfix）相对于 Base 发生变更，系统给出默认建议，但允许用户覆写。 |
| 交互一 | 扁平化分类导航 + 双栏（Hotfix vs Main）业务卡片对比。 |
| 交互二 | 实体列表 + 三栏（Hotfix / Base / Main）表单页面对比，差异单元格高亮。 |

## 3. 用户画像与核心场景

### 3.1 用户画像

**小王 - 业务域建模专员**
- 负责医院信息系统中住院业务域的模型维护。
- 不懂 Git，但熟悉医疗业务流程（医嘱、收费、护理记录）。
- 需要直观地看到"哪里改了"、"改了什么"。
- **偏好交互二**，因为平时在"编辑实体"页面工作，三栏对比的界面形态与日常工作一致。

**老张 - 版本管理员（业务域负责人）**
- 负责版本发布与 bugfix 合并。
- 关注合并安全性，不能因合并错误影响生产环境。
- 需要明确的冲突提示和一键裁决能力。
- **偏好交互一**，因为变更分类导航让他快速批量处理多个实体的冲突。

### 3.2 核心场景

#### 场景 A：无冲突自动合并（Happy Path）

> v2.0.0 已发布。生产环境发现"门诊医嘱"实体中缺少"加急标识"字段，且"获取门诊药品医嘱列表"方法的入参不够完整。
>
> 1. 老张从 `v2.0.0` Tag 拉出 `bugfix/v2.0.1-bugfix0002`。
> 2. 小王在 bugfix 中为"门诊医嘱"增加"加急标识"字段，同时优化了方法入参。
> 3. 同时，main 分支上另一名同事新增了"草药医嘱记录"实体。
> 4. 修复完成后，bugfix 状态变为"研发完成"，老张点击【合并】。
> 5. 系统检测到：双方修改互不重叠，**无冲突**。
> 6. 系统直接给出"无冲突"提示，老张确认后一键合并。

#### 场景 B：单边变更但用户希望覆写

> 承接场景 A，假设 bugfix 中把"门诊医嘱.打印次数"从"整数"改成了"打印频次"（名称变更），而 main 上将其类型改为了"长整数"。
>
> 由于 Base 上该字段为"整数"，Main 和 Hotfix 分别做了不同修改，系统判定为 **auto**。但系统默认建议采纳 Hotfix 的"打印频次"。老张核对后认为 main 的"长整数"更合理，于是点击"采纳 Main"进行覆写，再确认合并。

#### 场景 C：冲突需人工裁决（交互二体验）

> 小王使用交互二进行合并。打开弹窗后，左侧实体列表中"住院医嘱"带有红色"冲突"标记。
> 小王点击"住院医嘱"，右侧面板立即呈现三栏并排的实体编辑页：
> - 左栏 Hotfix："开立科室"的**名称**显示为"申请科室"（黄色高亮）。
> - 中栏 Base："开立科室"的**名称**显示为"开立科室"。
> - 右栏 Main："开立科室"的**名称**显示为"开单科室"（黄色高亮）。
> 小王点击高亮字段行，底部展开裁决区，他选择"采纳 Main"，冲突标记消失。

## 4. 产品范围（In / Out）

### 4.1 In Scope

- 基于 Base / Main / Hotfix 的语义级三方 Diff。
- 两套可视化交互：**交互一（结构化卡片）**与**交互二（表单三栏对比）**。
- 两套交互之间的自由切换入口（同一 BUG 修复列表页）。
- 冲突检测、分类导航（交互一）/ 实体列表导航（交互二）。
- 冲突裁决：采纳 Main / 采纳 Hotfix / 自定义编辑。
- Auto 合并的覆写机制。
- 合并结果生成与提交到 main 分支。
- 合并历史与状态变更（研发完成 → 已合并）。
- 版本发布管理页布局重构（版本列表移除、版本切换器下沉、全局/隔离视图区分）。
- 业务域设计页布局重构（业务模型切换页签置于建模子页签之上）。
- 所有操作列统一接入详情弹窗。

### 4.2 Out of Scope（本版本不做）

- 支持 feature 分支合并（仅支持 hotfix/bugfix → main）。
- 图片、文件附件的合并对比。
- 自动化测试用例的合并。
- 多人实时协同编辑冲突。
- 合并后自动生成回滚脚本（仅记录合并日志）。
- 交互二中字段级别的自定义 JSON 编辑（本版本仅提供"采纳左/右"）。

## 5. 功能需求

### 5.1 合并入口与交互切换

**入口位置**：`产品设计平台 > 版本发布管理 > BUG修复` 列表页。

**左侧交互切换栏**：
- 在页面主内容区左侧增加垂直切换栏，包含两个选项：
  - **交互一**：结构化对比（适合批量处理）。
  - **交互二**：表单三栏对比（适合细粒度核对）。
- 当前选中项高亮显示（蓝色边框 + 蓝色背景）。
- 切换交互模式时，表格数据保持不变，仅影响点击【合并】后弹出的弹窗类型。

**前置条件**：
- 仅当 bugfix 状态为 **"研发完成"** 时，操作列才显示【合并】按钮。
- 若 main 分支在 bugfix 创建后**未发生任何变更** → 系统执行 Fast-forward 合并，弹出轻量提示"合并成功"，无需进入决策弹窗。
- 若 main 分支**已发生变更** → 根据当前交互模式弹出对应的**合并决策窗口**。

### 5.2 冲突检测算法

**输入**：Base、Main、Hotfix 三个 JSON 对象（业务域模型）。

**判定规则（递归遍历 JSON 键）**：

| 场景 | Main vs Base | Hotfix vs Base | Main vs Hotfix | 判定结果 | 系统行为 |
|------|--------------|----------------|----------------|----------|----------|
| 未变更 | = | = | = | unchanged | 不展示 |
| 仅 Main 修改 | ≠ | = | — | auto | 建议采纳 Main，可覆写 |
| 仅 Hotfix 修改 | = | ≠ | — | auto | 建议采纳 Hotfix，可覆写 |
| 相同修改 | ≠ | ≠ | = | auto | 建议采纳任意一方 |
| 三方冲突 | ≠ | ≠ | ≠ | conflict | 必须人工裁决 |

**数组比较策略**：
- 若数组元素具备唯一业务标识（如字段 `id` 或 `code`），则按标识匹配后逐项比较。
- 若数组元素为纯值（如字符串列表），则按索引比较。
- 新增/删除的元素单独标记。

### 5.3 交互一：可视化对比界面

#### 5.3.1 布局

采用 **三栏式** 布局：
- **左栏（280px）**：变更分类导航（Tab 页签 + 扁平化卡片列表）。
- **中栏（flex:1）**：Hotfix（源分支）内容展示。
- **右栏（flex:1）**：Main（目标分支）内容展示。

**顶部工具条**：
- 分支流向：`Hotfix: v2.0.2-bugfix → Main`
- 冲突统计：未解决冲突数（红色）/ 可直接合并（绿色）
- 全局操作：全部采纳 Main / 全部采纳 Hotfix / 确认合并

#### 5.3.2 左侧导航设计

不再使用深层级树形控件，改用 **4 个 Tab 页签** 的扁平化列表：

- **冲突**：只展示 `mergeType = conflict` 的项，优先查看。
- **Hotfix**：只展示 Hotfix 侧有变更的项。
- **Main**：只展示 Main 侧有变更的项。
- **全部**：完整变更清单。

**卡片内容**：
- 业务路径（如 `住院医嘱 / 开立科室 / 名称`），过滤掉 `entities`、`fields` 等技术容器节点。
- 变更标签：冲突（红）、修改（黄）、新增（绿）、删除（红）。
- 已裁决的冲突显示绿色小字"已裁决: Main"。

**交互**：
- 打开弹窗时，**自动选中第一个冲突项**（如无冲突则选中第一项变更）。
- 点击卡片切换右侧详情，当前卡片高亮。

#### 5.3.3 中右对比区设计

**结构化渲染**：根据 JSON 节点类型自动识别为业务卡片：

| JSON 节点类型 | 界面渲染 | 示例 |
|--------------|----------|------|
| Entity | 实体卡片 | 🏥 患者信息 (Patient) |
| Field | 字段行 | 📋 姓名 / string / 必填 |
| Process | 流程卡片 | 🔀 医嘱流程：开立 → 审核 → 执行 |
| 原始值 | 文本块 | true / false / "DeptDict" |

**差异着色**：
- 🟢 绿色背景 = 新增
- 🔴 红色背景 + 删除线 = 删除
- 🟡 黄色背景 = 修改
- ⚠️ 橙色边框 = 冲突

### 5.4 交互二：表单三栏对比界面

#### 5.4.1 整体布局

采用 **左窄右宽** 布局：
- **左栏（160px）**：变更对象列表（实体 + 方法）。
- **右区（flex:1）**：三栏并排的实体编辑页或方法配置页对比（Hotfix / Base / Main）。
- **底部**：当前选中字段/参数的裁决区。

**顶部工具条**：
- 分支流向：`Hotfix → Base → Main`（三箭头依次排列）。
- 冲突统计与全局操作同交互一。

#### 5.4.2 左侧对象列表

只展示**发生变更**的实体和方法：
- 对象名称 + 英文编码 + 类型标签（实体/方法）。
- 状态标记：
  - 红色左边条 + "冲突"标签 = 该对象下存在未解决冲突。
  - 黄色左边条 + "变更"标签 = 该对象仅有 auto 变更。
- 点击对象切换右侧三栏内容。
- 打开弹窗时，**自动选中第一个带冲突的对象**。

#### 5.4.3 三栏对比区设计

每栏显示同一个对象在对应分支上的**编辑页**：
- 若当前对象为**实体**，显示"实体编辑页"（参考现有"编辑实体"弹窗布局，做窄窗口适配）。
- 若当前对象为**方法**，显示"方法配置页"（参考现有"方法配置"弹窗布局，做窄窗口适配）。

**实体基本信息区（顶部）**：
- 实体名称、构建名称、实体继承、系统实体、关联实体、关联模式、实体描述、功能模板（递归/排序/启停复选框）。
- 所有表单项采用 **2 列紧凑布局**，字号 12px，间距 8px，保证三栏并排在 1920px 及 1366px 屏幕下可读。

**中间 Tabs**：
- 默认显示"业务字段"Tab，其余 Tab（继承字段、功能配置、血缘详情）暂为空或占位。

**业务字段/入参表格（底部）**：
- 实体表格列宽：序号(45)、英文名称(90)、名称(80)、字段类型(70)、字段来源(60)、操作(50)。
- 方法入参表格列宽：序号(45)、参数名(90)、中文名(80)、数据类型(70)、是否数组(60)、来源(70)、操作(50)。
- 当某单元格的值相对于 Base 发生变化时，该单元格高亮：
  - 新增字段/参数：整行绿色背景。
  - 修改字段/参数：变化单元格黄色背景。
  - 删除字段/参数：整行红色背景 + 删除线。
  - 冲突字段/参数：变化单元格深黄色/橙色背景（与 auto 变更区分）。

#### 5.4.4 差异高亮规则

- **属性级高亮**：实体名称、实体描述、方法名称、技术类别等属性若发生变化，对应的表单项容器添加背景色。
- **字段/参数级高亮**：表格中仅对发生变化的单元格高亮，未变化单元格保持默认白色。
- **Base 栏**：仅作为参照，不做任何高亮。

### 5.5 交互式合并

#### 5.5.1 冲突节点裁决（交互一）

对 `mergeType = conflict` 的节点，详情区底部显示冲突裁决控件：

- **采纳 Main**：选中后右侧值生效。
- **采纳 Hotfix**：选中后左侧值生效。
- **自定义编辑**：弹出小型编辑器（字符串直接输入，对象/数组用 JSON 编辑器），允许手动修改值。

**约束**：
- 未裁决的冲突项 > 0 时，【确认合并】按钮置灰，并提示"请先解决 N 处冲突"。

#### 5.5.2 Auto 节点覆写（交互一）

对 `mergeType = auto` 的节点，系统给出默认建议，但保留用户覆写权限：

- 提示文案："系统建议采纳 **Hotfix** 的值，您也可以手动切换："
- 提供两个选项按钮：
  - `采纳 Main (true)`
  - `采纳 Hotfix (false)`
- 默认选中系统建议的一方。
- 下方实时显示"当前合并结果"预览。

#### 5.5.3 字段级裁决（交互二）

用户在三栏表格中点击带有"选"按钮的行（或点击高亮单元格），底部展开裁决区：

- 显示当前字段/参数在 **Hotfix / Base / Main** 三方的值。
- 提供两个操作按钮：
  - **采纳 Hotfix**（左栏值生效）
  - **采纳 Main**（右栏值生效）
- 若当前项为冲突，未选择前底部显示红色提示"该字段存在冲突，请先选择采纳 Hotfix 或 Main"。
- 若当前项为 auto 变更，用户仍可点击切换，切换后即时生效。

**批量裁决**：
- 顶部保留"全部采纳 Main"和"全部采纳 Hotfix"按钮，一次性处理当前所有未裁决项。

### 5.6 合并提交

**确认合并按钮状态**：
- 未解决冲突数 > 0：置灰。
- 所有冲突已裁决：可用。

**提交后执行**：
1. 根据用户裁决结果生成最终合并后的 JSON。
2. 向 main 分支提交合并后的业务域模型。
3. 更新 bugfix 状态为 **"已合并"**。
4. 生成合并记录（包含冲突数量、裁决详情、操作人、时间）。

**异常处理**：
- 若提交时 main 分支已被他人更新（版本号变化），提示"目标分支已更新，请重新打开合并窗口"。

## 6. 版本发布管理页布局（V2.2 更新）

- **移除左侧版本列表**：原版本发布管理页左侧的"版本列表" sidebar 已移除，释放更多横向空间给内容区。

## 8. CI/CD 协作流程（用户故事）

### 8.1 角色定义

| 角色 | 职责 |
|------|------|
| 设计人员 | 在业务域设计页完成实体/方法/接口/物理/事件建模，并提交模型至 main 分支。 |
| 研发人员 | 基于已发布版本进行编码实现；发现问题时新建 BUG，在 bugfix 分支修复并合并回 main。 |
| 测试人员 | 仅对包含多个业务域的"子系统"进行集成测试；子系统测试通过后更新测试状态。 |
| 业务域负责人（研发主管） | 审核设计变更、创建发布版本、监控 BUG 修复与合并进度，并在子系统测试通过后执行最终打版。 |

### 8.2 协作流程

1. **设计人员**完成业务域建模并提交至 main 分支。
2. **业务域负责人**在"版本发布管理"中审核变更记录，点击"提交测试"生成 main 版本（如 `main-v2.2.0`）。
3. **研发人员**基于该版本进行编码实现。
4. 若发现问题：
   - 研发人员在"BUG 修复"页新建 BUG，选择 bugfix 分支进行修复。
   - 修复完成后，BUG 状态变为"研发完成"，点击"合并"通过可视化合并工具（交互一/交互二）将修复合回 main。
5. 若正常完成：研发工作直接结束，进入测试阶段。
6. **测试人员**对子系统进行集成测试。测试通过后，子系统测试状态回传至下属各业务域。
7. **业务域负责人**确认业务域"研发完成"且"子系统测试通过"，执行最终打版，触发 CI/CD 流水线发布。

### 8.3 关键约束

- **测试状态回传**：业务域本身不维护独立的测试入口。子系统测试通过后，由测试平台通过接口回传，批量更新该子系统下所有关联业务域的测试状态。
- **分支策略**：main 用于日常设计与稳定发布；bugfix 用于紧急缺陷修复。修复完成后必须通过合并工具解决冲突后方可合入 main。

## 9. 非功能需求

### 9.1 性能
- 业务域 JSON 大小通常在 1MB 以内，Diff 算法需在 **500ms** 内完成。
- 合并弹窗打开到首屏渲染时间 < 1s。

### 9.2 兼容性
- 支持未知 JSON 键的透传，确保未来模型扩展不会导致合并失败。
- 兼容 Chrome 90+、Edge 90+。

### 9.3 可回滚
- 合并操作生成版本记录，支持在"血缘日志"中查看并回滚到合并前状态（本版本仅记录，回滚入口在血缘日志模块）。

### 9.4 响应式
- 合并弹窗适配 1920×1080 及 1366×768 分辨率。
- 左栏导航支持纵向滚动，卡片宽度自适应。
- 交互二三栏区域在 1366px 下允许横向滚动，确保表格内容可读。

## 11. 风险与应对

| 风险 | 影响 | 应对措施 |
|------|------|----------|
| 业务人员不理解 diff3 的 auto 合并逻辑，误以为系统"擅自修改了模型" | 高 | 在 auto 节点提供**建议来源说明** + **一键覆写按钮**，并显示合并结果预览。 |
| 交互二三栏并排导致 1366px 屏幕下表格过窄无法阅读 | 中 | 精简表格列宽、表单项 2 列紧凑布局；超出区域提供横向滚动。 |
| JSON 结构升级后旧 Diff 算法出现匹配错位 | 中 | 数组比较优先使用 `id` 匹配，未知字段透传；算法层增加异常兜底。 |
| 合并后业务域模型在生产环境引发故障 | 高 | 合并前强制进入决策窗口（除 Fast-forward 外），合并后生成版本记录支持血缘追溯。 |
| 大型 JSON（>5MB）导致 Diff 卡顿 | 低 | 算法层采用递归而非全量序列化；性能超过 1s 时增加 Loading 提示。 |
