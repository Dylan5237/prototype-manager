# 伏羲平台更新公告｜2026-09-09

本次更新主要围绕 **AI 助手接入稳定性** 与 **项目内 AI 修改协作流程** 两条主线进行升级。

## 一、AI 助手接入流程升级

### 1. 显式选择当前 AI Host
接入平台 MCP 时，由用户明确选择当前使用的 AI Host，不再通过本地目录或运行环境推断当前客户端。

当前接入策略：
- **WorkBuddy**：推荐并稳定支持；
- **Cursor**：兼容支持；
- **Codex**：当前不提供确定性自动安装配置；
- **其他 Host**：仅进行能力发现，不自动猜测配置路径。

### 2. 接入流程改为确定性程序执行
平台生成的接入提示词只负责触发统一 onboarding 程序。下载、校验、安装、配置、认证和验证等确定性步骤由程序执行，减少 AI 在安装过程中的自由发挥和环境侦察。

### 3. MCP / Skill 版本校验更可靠
接入程序会同时校验 MCP 与 Skill artifact SHA-256。只有两者都与当前平台发布版本一致时，才允许判定为 `ALREADY_COMPLETE`。

如果本地仍是旧版本，会执行真实升级，不再因为旧 bootstrap 记录而错误跳过更新。

### 4. 接入后的验证方式
完成接入或升级后，建议：
1. 按客户端要求完成终端执行授权；
2. 如 WorkBuddy 提示信任自定义连接器，在「连接器 → 自定义连接器」中信任 `fuxi-platform`；
3. 重新加载客户端或新开会话；
4. 由 AI 调用 `check_connection` 并确认连接已验证；
5. 确认伏羲 MCP 工具已正常加载。

## 二、项目内 AI 修改升级为 Task v2

项目中的 AI 修改不再以旧 `changeId` 写入链路作为主流程，而统一进入任务账本。

标准流程调整为：

```text
创建任务 → 接受任务 → AI 提交修订 → 人工审核 → 退回或采用 → 形成正式版本
```

### 1. 一个任务只保留一个当前待审修订
同一任务最多只有一个 `ready` 状态的待审候选。再次提交时，旧待审候选会转入历史，不会出现多个候选同时等待负责人判断。

### 2. 审核界面改为“正式版 vs 待审修订”
审核主界面直接展示：
- 当前正式版；
- 当前唯一待审修订；
- 修订说明；
- 「退回」与「采用为正式版」操作；
- 可折叠查看的历史尝试。

### 3. 支持退回后再次提交
负责人可以退回当前修订，AI 根据反馈继续修改并重新提交。再次提交不会覆盖历史记录。

### 4. 采用后形成新的正式版本
只有经过有权限的审核者执行“采用为正式版”后，待审修订才会进入正式版本。AI 提交候选本身不会直接覆盖线上正式内容。

### 5. 旧项目写入链路安全关闭
旧版项目写入方式会返回 `LEGACY_CHANGEID_FORBIDDEN`，防止新旧两套项目修改账本并行写入导致状态不一致。

独立原型修改仍保留 `directChangeId` 流程，不受项目 Task v2 影响。

---

## 三、对现有用户的影响

- 原有项目和原型继续可访问；
- 独立原型的快速修改方式保持兼容；
- 项目内 AI 修改请从当前平台页面重新生成任务/提示词，不要继续复用旧版项目修改会话或旧提示词；
- 已接入 MCP 的用户在再次执行接入/升级流程时，会根据 artifact SHA 判断是否需要真实升级；
- 更新 MCP / Skill 后建议重新加载客户端或新开会话。

本次升级的核心目标是：**让 AI 少做不确定判断，让确定性程序负责安装与执行；让项目中的 AI 修改成为可协作、可审核、可追踪的正式工作流。**

—— 伏羲平台团队
