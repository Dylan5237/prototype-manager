# 伏羲评优有效使用指标模型

## 一、结论

评优统计页的目标不是“给伏羲自己打分”，而是提供**可直接用于评委评分、且能够被数据库/日志/任务记录复核的原始指标与计算结果**。

核心原则：

1. **事件不等于有效使用**。登录、访问、刷新、按钮点击、接口调用、AI 重试、分享链接生成等，都是底层事件，只能作为证据，不能直接计为一次有效使用。
2. **有效使用的最小统计单元是“真实业务任务”**。一次真实业务需求，从发起到形成可追溯结果，才计为一次有效使用；同一业务任务中的多次 AI 调用、上传、修改、预览和重试不重复计数。
3. **用户有效使用人数按“完成至少一个有效业务任务的目标用户”去重计算**。
4. **分享和预览是重要使用链路，但不能天然等于有效用户**。匿名免登录访问若无法确认真实身份、部门和目标用户归属，只能作为使用触达/评审证据，不能直接计入有效用户覆盖率。
5. **所有指标必须可下钻**。页面上的任何数字，都应能解释：分子、分母、时间范围、排除规则、数据来源和对应明细。
6. **评分页展示“评分输入”，不展示自评得分**。例如展示覆盖率 73.3%、准确率 95%、节时率 62.4%，不展示“使用广度 4 分”“预计总分 88 分”。

---

## 二、官方规则对统计口径的约束

官方评优要求：

- 有效使用必须对应真实业务任务；
- 内部测试、重复刷新、无效调用、批量造数不得计入；
- 目标用户按工具实际服务岗位确定，不按部门总人数扩大；
- 使用数据必须有后台日志、任务记录、案例、用户反馈、耗时对比等证据；
- 使用频率以有效使用次数为基础；同一场景应用的多次调用不应重复计数；
- 准确可靠需要代表性案例及业务复核；
- 效率与效果需要同类任务前后耗时对比，并包含人工复核和修改时间。

因此，伏羲当前“访问 / 原型 / 版本 / 行为事件”统计是基础数据层，不应直接等同于评优指标层。

---

## 三、数据模型：事件 → 业务任务 → 评优指标

建议把统计体系分成三层。

### 1. Event：原子事件层

用于记录真实行为证据，例如：

- 登录/访问；
- 生成接入提示词；
- MCP/Skill 接入成功；
- 创建原型任务；
- 上传原型；
- 形成版本；
- 修改独立原型；
- 发起项目修改任务；
- 提交待审修订；
- 退回；
- 采用为正式版；
- 生成分享链接；
- 免登录分享访问；
- 普通预览；
- 版本读取；
- 错误/失败；
- 重试。

Event 只作为证据，不直接累计为“有效使用次数”。

### 2. Business Task：真实业务任务层

把属于同一个真实业务目标的一系列事件聚合成一个任务单元。

示例：

```text
产品经理提出“新增异常订单详情页”
→ 生成任务提示词
→ AI 修改 3 次
→ 上传 2 次
→ 形成 2 个候选
→ 负责人退回 1 次
→ 第二次提交
→ 采用为正式版
→ 分享给业务方预览
```

评优口径：**有效使用次数 = 1**，而不是 10+。

### 3. Evidence：人工/半自动证据层

用于补充行为日志无法证明的指标：

- 是否真实业务需求；
- 是否业务复核通过；
- 是否严重错误；
- 传统方式耗时；
- 伏羲方式人工复核时间；
- 返工时间；
- 用户反馈；
- 跨部门联系人确认。

准确率和节时率必须来自该证据层，不应由普通点击日志反推。

## 四、按用户完整使用路径重新定义有效使用

### 路径 A：首次接入

典型行为：

```text
登录伏羲
→ 点击“接入平台 MCP”
→ 选择 AI 软件
→ 生成提示词
→ AI 执行接入
→ 新会话连接验证成功
```

统计判断：

- “访问伏羲”：不是有效使用；
- “生成接入提示词”：不是有效使用；
- “接入成功”：属于**激活指标**，证明用户具备后续使用条件；
- 仅完成接入但没有完成真实业务任务，不计入评优“有效用户”。

建议统计：

- 已接入用户数；
- 接入成功率；
- 从接入成功到首次有效业务任务的转化率；
- 首次有效任务耗时。

这些属于诊断指标，不直接作为官方使用广度分子。

### 路径 B：创建 / 上传新原型

典型行为：

```text
真实需求
→ 让 AI 创建
→ AI 实现
→ 上传/交付
→ 形成可读取版本
→ 预览成功
→ 用户验收
```

满足以下条件时，可形成一条有效业务任务：

- 发起人可识别；
- 任务不是测试/验收/运维造数；
- 有真实业务目标；
- 最终形成可追溯原型/版本；
- 真实预览可打开或有等价平台 readback；
- 任务未被标记为无效。

AI 重试、多次上传、多个版本尝试只属于该任务的执行过程，不重复计数。

### 路径 C：独立原型修改 / 更新

典型行为：

```text
现有原型
→ “让 AI 修改”
→ 形成修改结果
→ 新版本
→ 预览/验收
```

一次独立的业务修改需求计为 1 次有效使用。

同一需求里的：

- 多轮提示；
- 多次上传；
- 多版本尝试；
- 预览刷新；

均不能重复累计。

### 路径 D：项目内修改与审核

典型行为：

```text
发起修改任务
→ AI 提交待审修订
→ 负责人查看
→ 退回 / 重新提交
→ 采用为正式版
```

这里要区分两种统计对象：

1. **业务任务次数**：整条修改链路计 1 次；
2. **有效用户人数**：发起者/编辑者/负责人是否分别计入，要看其是否完成了真实业务角色动作。

建议：

- 编辑者完成一次真实项目修改任务，可以计为有效用户；
- 负责人完成真实审核动作（查看修订并退回或采用），可以计为有效用户；
- 只是打开任务页面但没有实际审核，不计。

这样可以反映伏羲不仅服务“原型生产者”，也服务“审核协作者”。

### 路径 E：生成免登录分享链接

仅“生成分享链接”不能单独算一次有效使用，因为它可能从未真正被访问。

建议把分享定义为任务链中的传播/评审阶段：

```text
生成分享链接
→ 分享给真实评审者
→ 至少一次有效预览成功
```

如果分享属于前述创建/修改任务的自然后续，不再额外增加“有效使用次数”，避免同一业务任务被拆成多次使用。

但可以单独统计：

- 分享任务数；
- 产生真实访问的分享数；
- 分享转化率；
- 唯一访问者数；
- 分享预览成功率。

### 路径 F：其他用户通过免登录链接预览

这是目前最容易误算的路径。

匿名访问如果无法确认真实人员身份、所属部门、是否属于目标用户，则：

- 可以计为“分享访问 / 评审触达”；
- 可以证明伏羲结果被真实消费；
- **不能直接计入有效用户覆盖率**；
- 不能用于跨部门有效用户人数。

只有在以下情况之一成立时，才建议把评审者计入有效用户：

- 登录用户可明确识别；
- 分享邀请与具体人员绑定；
- 有可验证的评审身份/部门映射；
- 有明确业务评审动作而不只是页面打开。

否则页面应把它单独展示为“匿名/免登录有效预览人数（会话）”。

### 路径 G：普通用户预览已有原型

单纯打开预览不应直接等于有效使用。

建议区分：

- **浏览行为**：页面打开；
- **有效评审行为**：打开真实业务原型，并完成一个明确业务动作，例如审核、反馈、确认、采用或分享链路中的真实评审。

如果当前平台没有反馈/确认等显式动作，则普通预览应作为辅助使用证据，不宜直接进入“有效使用次数”。

## 五、官方可评分指标的计算模型

### 1. 目标用户数

来源：目标用户注册表/人员清单，而不是行为日志自动推断。

规则：

- 按实际服务岗位界定；
- 冻结统计期口径；
- 人员离职/转岗需保留变更记录。

### 2. 有效用户数

公式：

```text
有效用户数 = 统计期内完成 >=1 个有效业务任务的目标用户去重数
```

可计入角色：

- 原型创建者；
- 修改者；
- 项目任务编辑者；
- 真实审核负责人；
- 可识别且完成真实评审动作的目标用户。

不计：

- 仅登录；
- 仅接入；
- 仅刷新；
- 仅内部测试；
- 无身份匿名访问；
- 只打开页面但没有形成真实业务动作。

### 3. 目标用户覆盖率

```text
覆盖率 = 有效用户数 / 目标用户数
```

统计页必须同时展示分子和分母，例如：

```text
有效用户 22 / 目标用户 30 = 73.3%
```

禁止只展示 73.3% 而隐藏人数。

### 4. 有效使用次数

```text
有效使用次数 = 去重后的真实业务任务数
```

建议按任务类型拆分：

- 创建新原型；
- 上传已有原型；
- 独立原型修改；
- 项目内修改；
- 项目审核；
- 其他经确认的真实业务任务。

注意：同一业务任务中的上传、版本、候选、分享、预览、AI 重试不能重复累计。

### 5. 重复使用人数

```text
重复使用人数 = 统计期内完成 >=2 个不同有效业务任务的用户去重数
```

建议同时展示：

```text
重复使用率 = 重复使用人数 / 有效用户数
```

不把同一个业务任务里的连续点击/重试当成重复使用。

### 6. 使用频率

统计页应优先展示透明的原始输入：

- 有效业务任务总数；
- 人均有效任务数；
- 重复使用人数；
- 重复使用率；
- 按周有效任务趋势。

如果后续官方明确“目标使用达成率”的分母定义，再增加：

```text
目标使用达成率 = 实际有效任务数 / 统计期预先冻结的目标任务数
```

在分母未被明确冻结前，不应为了评分自行构造一个“使用频率得分”。

### 7. 跨部门使用

按可识别用户和有效业务任务计算：

- 有效使用部门数；
- 各部门有效用户数；
- 各部门有效业务任务数；
- 跨部门重复使用情况。

匿名分享访问不能直接用于跨部门计数。

### 8. 准确可靠

只能基于“已复核案例”计算。

```text
准确率 = 复核通过案例数 / 纳入复核案例总数
```

同时展示：

- 复核案例数；
- 通过数；
- 不通过数；
- 严重错误数；
- 复核规则版本；
- 复核人；
- 关联业务任务。

不能从“版本成功生成”“预览 HTTP 200”推断业务准确。

### 9. 效率与效果

以配对样本为基础：

```text
伏羲总耗时 = AI/工具执行时间 + 人工复核时间 + 人工返工时间

单样本节时率 = (传统方式耗时 - 伏羲总耗时) / 传统方式耗时
```

统计页建议同时展示：

- 配对样本数；
- 传统方式总耗时；
- 伏羲方式总耗时；
- 人工复核总耗时；
- 返工总耗时；
- 总体节时率；
- 节时率中位数；
- 是否存在质量下降案例。

总体节时率建议使用：

```text
(Σ传统耗时 - Σ伏羲总耗时) / Σ传统耗时
```

这样大任务与小任务按真实耗时贡献加权，同时再展示中位数防止个别超大任务扭曲结果。

## 六、新统计页应该怎么设计

建议不再把“有效使用闭环”作为评分页主结构。当前漏斗适合产品运营，但容易让人误解“经过四步 = 一次评分使用”。

新的“评优数据”页建议分四块。

### A. 官方评分输入指标

顶部卡片直接展示：

- 目标用户数；
- 有效用户数；
- 目标用户覆盖率；
- 有效业务任务数；
- 重复使用人数 / 重复使用率；
- 有效使用部门数；
- 准确性复核样本数 / 准确率 / 严重错误数；
- 效率配对样本数 / 总体节时率；
- 质量下降案例数。

不展示：

- “使用广度 4 分”；
- “预计总分”；
- “冲奖等级”。

### B. 业务使用路径

用于解释指标来源，而不是直接评分：

```text
接入成功
→ 首次真实业务任务
→ 创建/上传/修改
→ 形成版本或待审修订
→ 审核/采用
→ 分享
→ 真实预览/评审
```

每一阶段显示用户数、任务数和转化率，用于诊断为什么有效使用没有形成。

### C. 任务结构与部门分布

展示：

- 创建 / 上传 / 独立修改 / 项目修改 / 审核任务结构；
- 各部门目标用户、有效用户、任务数；
- 首次使用与重复使用；
- 周趋势。

### D. 证据与可审计性

每个指标必须提供“查看明细”，能够下钻到：

- user_id；
- department；
- business_task_id；
- prototype_id；
- version / candidate（如适用）；
- 开始/完成时间；
- 是否有效；
- 排除原因；
- 原始事件/日志引用；
- 人工复核记录；
- 效率样本记录。

---

## 七、每个指标必须显示的数据血缘

统计页每个数字建议统一附带：

- **统计时间范围**；
- **公式**；
- **分子**；
- **分母**；
- **排除规则**；
- **数据源**；
- **最后更新时间**；
- **明细入口**。

示例：

```text
目标用户覆盖率 73.3%
22 / 30
统计期：2026-09-16 ～ 2026-11-15
数据源：目标用户名单 + 有效业务任务聚合
排除：测试账号、内部验收任务、匿名分享访问、无效/重复任务
更新时间：2026-10-01 09:00
[查看 22 名有效用户] [查看 30 名目标用户] [查看排除记录]
```

这比“平台告诉评委我们是 4 分”可信得多。

---

## 八、当前伏羲现有统计页的判断

现有“使用总览”已经具备很好的底座：

- 周期内有效用户；
- 再次使用用户；
- 激活率；
- 有效产出用户；
- 有效使用闭环；
- 趋势；
- 活跃原型；
- 来源/角色等过滤。

但如果用于本次评优，仍需完成从“产品行为分析”到“可审计评优指标”的转换：

1. 把“用户行为事件”聚合为“真实业务任务”；
2. 明确目标用户注册表；
3. 对内部测试/验收/自动化任务做显式排除；
4. 区分接入激活、业务生产、审核、分享、匿名预览；
5. 匿名分享访问不得混入有效用户覆盖率；
6. 增加部门维度和跨部门真实任务统计；
7. 增加准确性案例表和效率配对样本表；
8. 每个指标支持数据血缘和明细下钻；
9. 页面只展示评分输入，不生成自评得分。

---

## 九、建议的最小改造优先级

### P0：统计期开始前必须完成

- 冻结目标用户清单；
- 定义并实现 business_task_id / 等价任务聚合规则；
- 测试/验收/机器人/无效任务排除；
- 部门归属；
- 有效用户、有效任务、重复使用的可审计计算；
- 指标明细下钻。

### P1：统计期早期完成

- 分享/匿名预览单独口径；
- 项目审核者有效使用口径；
- 准确性案例登记与复核；
- 效率样本登记与计算；
- 数据来源/公式透明展示。

### P2：用于最终材料优化

- 跨部门证明视图；
- 代表案例一键导出；
- 周度数据快照；
- 最终申报指标导出。

---

## 十、最终原则

伏羲新的评优统计页应做到：

> **不证明“我们觉得自己很好”，而证明“真实用户在真实业务任务中怎样使用伏羲，以及这些结果为什么可以被复核”。**

页面上的每一个指标都应该可以追溯到数据库记录、服务日志、任务记录或明确的人工复核证据。评委需要打分时，直接拿这些透明指标代入官方评分规则即可。
