# 申报决策记录

本文件记录会影响统计口径、奖项策略、证据解释或最终申报叙事的重要决定。不要覆盖旧决定；如发生变化，追加新条目并说明取代关系。

## DEC-001｜奖项策略

- 日期：2026-09-11
- 状态：Accepted
- 决策：主攻“专业场景提效奖”；若统计期内完成至少两个相互独立部门/业务单元的真实使用验证，则同时申报“AI 赋能综合示范奖”。
- 原因：专业场景奖对“效率与效果”权重 40%，与伏羲当前价值优势更匹配；综合示范奖更依赖使用广度和跨部门复制。

## DEC-002｜申报定位

- 日期：2026-09-11
- 状态：Accepted
- 决策：对外申报名称建议为“伏羲平台——AI 驱动的原型生产与协作工具”。
- 主叙事：需求描述 → AI 原型生成 → 修改迭代 → 人工审核 → 版本沉淀 → 分享评审。
- 不作为主叙事：MCP、Task v2、Harness 等内部技术实现名词。

## DEC-003｜有效使用口径

- 日期：2026-09-11
- 状态：Proposed，需 2026-09-15 前冻结
- 建议定义：一个真实业务需求，通过伏羲完成一次可被验收的原型创建或修改任务，并在平台形成可追溯结果，计为一次有效使用。
- 不计入：内部测试、重复刷新、单次底层调用、同一业务任务中的 Agent 技术重试、批量造数。

## DEC-004｜效率测量原则

- 日期：2026-09-11
- 状态：Proposed，需 2026-09-15 前冻结
- 决策：传统方式与伏羲方式必须使用可比较的同类任务口径；伏羲成本包含人工准备、复核和必要返工，不允许只取 AI 生成时间。
- 建议公式：`节时率 = (传统方式总耗时 - 伏羲方式总耗时) / 传统方式总耗时`。
