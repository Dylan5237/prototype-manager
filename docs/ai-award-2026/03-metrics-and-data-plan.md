# 统计期指标与数据采集方案

## 一、有效使用定义

建议把“有效使用次数”定义为：

> 一个真实业务需求，通过伏羲完成一次可被验收的原型创建或修改任务，并在平台形成可追溯结果。

建议同时满足：

1. 对应真实业务需求；
2. 用户发起创建或修改；
3. AI 实际执行；
4. 伏羲形成原型、版本或待审修订；
5. 用户完成至少一次预览、审核或结果确认。

以下行为不单独计为有效使用：

- 登录；
- 页面刷新；
- 单次生成提示词；
- MCP/Agent 底层重复调用；
- 同一业务任务中的多轮重试；
- 测试数据或内部验收造数。

## 二、统计字段建议

统计期开始前，至少保证可以还原以下字段：

| 字段 | 用途 |
|---|---|
| task_id / prototype_id | 任务去重和追溯 |
| user_id | 去重活跃人数 |
| 用户部门/业务单元 | 跨部门统计 |
| 用户岗位 | 目标用户口径 |
| 任务类型 | 新建 / 独立修改 / 项目修改 |
| 真实业务场景 | 判断是否有效使用 |
| 发起时间 | 效率分析 |
| 完成时间 | 效率分析 |
| 人工复核分钟数 | 计算真实总成本 |
| 是否成功 | 准确率 |
| 是否严重错误 | 最高档准确可靠门槛 |
| 是否返工 | 质量变化 |
| 最终是否采用 | 结果有效性 |
| 用户反馈 | 业务证据 |
| 平台版本 | 复现和追溯 |

原则：优先复用现有平台日志和任务记录，只补真正缺失的数据，不为了评奖单独造一套复杂系统。

## 三、五个评分项的内部目标

### 1. 使用广度

核心指标：

**有效使用人数 ÷ 目标用户人数**

建议目标：

- 最低目标：≥60%
- 冲高目标：≥80%

目标用户池必须真实、稳定，并在统计期开始前尽量冻结。

### 2. 使用频率

建议在统计期前设定目标使用量，例如：

> 每位目标用户在统计期内完成至少 3 个真实业务任务。

然后计算：

**实际有效任务数 ÷ 计划有效任务数**

具体目标值可根据目标用户规模再校准，但不应在统计期结束后倒推。

### 3. 准确可靠

建议准备 10～20 个代表性案例，统一验收维度：

- 需求理解是否正确；
- 页面是否完整；
- 关键交互是否完成；
- 预览是否可正常打开；
- 交付目标是否正确；
- 版本是否正确；
- 是否存在严重业务错误。

建议内部定义“严重错误”为：

- 错误覆盖正式原型；
- 修改了错误目标；
- 造成不可接受的数据或版本损坏；
- 暴露敏感信息；
- 交付结果不可恢复；
- 其他会使真实业务无法继续的重大问题。

冲高目标：

- 正确率 ≥95%；
- 且无严重错误。

### 4. 流程规范化

伏羲当前已有较好基础，重点不是继续加功能，而是把现有事实转成证据：

- 统一正式入口；
- Help Center / 操作说明；
- 负责人；
- 版本和 release 记录；
- 任务与操作日志；
- 反馈闭环；
- 持续更新记录；
- 项目内审核流程。

### 5. 效率与效果

这是专业场景提效奖的胜负手。

每个样本都建议记录：

- 传统方式总耗时；
- 伏羲 AI 执行时间；
- 人工复核时间；
- 必要返工时间；
- 最终质量结果。

伏羲总耗时：

**AI 执行 + 人工复核 + 必要返工**

节时率：

**（传统人工总耗时 - 伏羲总耗时）÷ 传统人工总耗时**

示例：

- 传统人工：180 分钟
- 伏羲总耗时：45 分钟
- 节时率：75%

建议至少形成 10～20 组配对数据。

## 四、专业场景提效奖冲分目标

建议把内部目标设置为：

| 指标 | 权重 | 内部目标评价 | 目标加权分 |
|---|---:|---:|---:|
| 使用广度 | 15 | 4/5 | 12 |
| 使用频率 | 10 | 4/5 | 8 |
| 准确可靠 | 25 | 5/5 | 25 |
| 流程规范化 | 10 | 4/5 | 8 |
| 效率与效果 | 40 | 5/5 | 40 |
| 合计 | 100 |  | 93 |

如果效率最终只能达到 50%～79% 节时，对应 4/5，该项约 32 分，整体仍可达到约 85 分级别。

不要为了冲 5 分人为优化口径。真实、可复核的 60%～70% 节时率，比无法解释的极高节时率更有可信度。

## 五、建议周度看板

从 2026-09-16 开始，每周至少跟踪：

- 目标用户数；
- 本周新增有效用户；
- 累计去重有效用户；
- 本周有效任务数；
- 累计有效任务数；
- 重复使用人数；
- 成功率；
- 严重错误数；
- 平均节时率；
- 已完成效率对比样本数；
- 已沉淀代表案例数；
- 已覆盖部门/业务单元数。

出现数据口径问题，应尽量在统计期前半段修正并留下变更说明，避免统计期结束时临时重算。
