# 伏羲申报定位与可行性分析

## 一、申报定位

建议统一使用以下对外申报名称和业务表述：

**伏羲平台——AI 驱动的原型生产与协作工具**

核心场景：

> 帮助产品、需求及相关研发人员，把“需求描述 → AI 原型生成 → 修改迭代 → 人工审核 → 版本沉淀 → 分享评审”形成统一闭环。

核心价值主张：

1. 缩短原型制作时间；
2. 降低反复沟通和返工成本；
3. 把 AI 原型生产从个人临时行为转化为有入口、有规范、有记录、可复用的标准流程。

申报材料不建议把“MCP 平台”“Agent Harness”“Task v2”等技术实现作为主叙事。技术能力可以作为可靠性和流程治理的支撑证据，但评委首先需要理解业务问题、使用方式和效果。

## 二、目标用户定义

建议定义为：

> 经常承担需求分析、产品方案设计、页面原型制作或需求评审工作的产品经理、需求分析人员及相关研发人员。

目标用户人数必须按实际服务岗位统计，不以整个部门人数作为分母。

## 三、当前申报可行性

| 项目 | 当前判断 | 说明 |
|---|---|---|
| 申报资格 | PASS | 定位为公司内部 AI 赋能工具，不作为对外商业化产品申报 |
| 正式入口 | PASS | 已有正式环境和统一平台入口 |
| 真实业务闭环 | PASS | 已覆盖创建、修改、版本、项目协作、审核、预览和分享 |
| 流程规范化 | 强项 | 已具备手册、统一接入、版本管理、发布、日志和任务闭环 |
| 准确可靠 | 有基础 | 需要把真实案例转化为统一可复核的测试样本 |
| 使用广度 | 待统计 | 需在统一统计期内形成去重活跃用户数据 |
| 使用频率 | 待统计 | 需冻结“有效使用”的业务口径 |
| 效率与效果 | 高潜力 | 需要建立人工方式与伏羲方式的成对耗时对比 |
| 综合示范奖跨部门条件 | 待验证 | 需至少两个独立部门或业务单元真实使用 |
| 专业场景提效奖匹配度 | 高 | 该奖项 40% 权重集中在效率与效果，和伏羲价值高度一致 |

## 四、奖项策略

### 主攻：专业场景提效奖

原因：

- 允许专业岗位、小规模目标用户；
- “效率与效果”权重 40%，是最大单项；
- “准确可靠”权重 25%；
- 伏羲已有较强流程规范化基础；
- 不需要先证明大规模横向推广才能有竞争力。

核心打法：

> 用 10～20 组真实任务证明：在包含人工复核和必要返工后，伏羲仍显著缩短原型生产时间，并保持质量不下降。

### 条件满足后：同时申报 AI 赋能综合示范奖

建议设置内部 Gate：

**2026-10-15 前，如果已经有至少两个相互独立部门或业务单元持续产生真实有效任务，则启动综合示范奖材料；否则集中资源主攻专业场景提效奖。**

综合示范奖的核心不是“技术更先进”，而是证明：

> 伏羲不仅在一个团队有效，而且能够被不同团队复制使用。

## 五、建议的评委叙事

申报和答辩时，优先围绕以下逻辑展开：

### 过去怎么做

需求人员依赖人工原型工具或临时 AI 对话完成页面设计，生成、修改、版本、协作和验收分散在不同工具和个人习惯中。

### 伏羲怎么做

用户从统一入口发起 AI 创建或修改任务；AI 完成实现和交付；平台保留版本、预览和项目协作记录；项目内修改经过人工审核后才成为正式版本。

### 产生什么结果

用真实数据证明：

- 单个原型任务总耗时下降；
- 人工复核时间可控；
- 返工率没有明显恶化；
- 交付结果可追溯；
- 不同用户可以使用同一套流程完成任务。

## 六、当前最大风险

当前最大风险不是功能不足，而是**缺少连续、统一、可复核的价值数据**。

因此统计期开始前应优先解决：

1. 目标用户清单；
2. 有效使用定义；
3. 任务去重规则；
4. 成功/失败和严重错误定义；
5. 人工基准耗时采集方法；
6. 伏羲总耗时采集方法；
7. 代表性案例留存；
8. 用户部门和岗位信息；
9. 用户反馈和复用证明。

不建议为了评奖继续堆功能。接下来应把部分重点从“继续建设产品”切换到“证明产品已经产生真实业务价值”。
