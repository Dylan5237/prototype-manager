# 团队协同 MVP 原型

> 全量产品与技术设计见 [FULL_DESIGN.md](./FULL_DESIGN.md)。

## 定位

伏羲仍是“AI 生产的原型的托管平台”。MVP 不提供网页代码编辑器，也不把 GitLab 的复杂操作复制到平台。平台把 Git 分支、构建、合并请求和版本锁定翻译成操作者能理解的任务状态。

## 已对齐的产品约束

- 一个原型对应一个由伏羲供应的远程 Git 仓库，V1 物理托管在专属 GitLab 命名空间。
- 项目是唯一业务权限边界。平台管理员或项目管理员只负责把用户加入项目，平台自动派生项目内协作权限。
- 项目成员可以为归属项目内的原型创建工作分支、提交修改和发起审核；项目管理员负责合并与项目发布。
- 禁止直接写 `main`。每项修改使用独立工作分支，通过合并请求进入 `main`。
- 平台只检测和展示 Git 冲突，不自动猜测解决。
- 合并前固定检查：构建、预览、跨原型导航契约、安全内容。
- 合并 `main` 自动生成不可变原型版本，但不会自动升级项目。
- 项目草稿显式选择原型版本；发布后形成锁定 commit 和构建制品的不可变 manifest。
- 原型独立构建，通过稳定 `routeKey + navigate` 契约完成跨原型页面跳转。
- Agent 是项目成员的短期受托执行者，不能合并、发布或管理成员。

## 原型覆盖的任务闭环

1. 项目管理员添加成员，平台自动完成权限配置。
2. 成员从“让 AI 修改”描述目标，伏羲生成并复制带最新项目入口的任务提示词。
3. 用户把提示词粘贴到本地 Agent；Agent 连接伏羲获取权威上下文，在后台准备工作分支并执行修改。
4. 分支构建成功后生成独立预览并进入修改审核。
5. 管理员查看效果，合并后自动生成原型版本。
6. 管理员选择新版本，验证整项目后发布。

## 交互原则

- 首屏只回答一个问题：我下一步需要做什么。
- Git 术语只作为二级信息出现；主按钮使用“让 AI 修改、查看效果、合并修改、发布项目”。
- 正常链路只暴露一个主操作；异常状态解释影响并给出唯一恢复入口。
- 版本升级必须显式选择，任何原型更新都不会悄悄改变已发布项目。
- 权限来源不要求操作者配置：成员进入项目后由平台自动开通协作能力。
- 首页不展示统计、动态、commit、构建明细或权限说明；这些信息只在用户处理对应任务时按需出现。

## 查看方式

直接通过本地 HTTP 服务打开 `index.html`。原型为单文件、无外部依赖，包含管理员/成员视角切换以及关键流程的模拟交互。
