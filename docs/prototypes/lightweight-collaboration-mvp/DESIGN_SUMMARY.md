# 伏羲轻协作 MVP 设计摘要

> 设计基线：2026-08-20
> 状态：方向已确认，随实现同步验证

## 1. 结论

伏羲轻协作 MVP 让项目成员把一次 AI 修改作为候选版本交给负责人预览和采用，全程不要求任何人理解或操作 Git。

## 2. 用户与核心任务

| 项目 | 已确认答案 |
|---|---|
| 主用户 | 发起修改的项目成员、负责采用结果的项目负责人 |
| 触发 | 成员在项目原型上点击“让 AI 修改”并描述目标 |
| 核心动作 | Agent 领取一次性任务、下载当前源码、上传可预览候选包 |
| 可观察结果 | 负责人看到候选预览，采用后原型生成一个新的正式版本 |
| 最高成本失败 | 基于旧版本的候选静默覆盖已经采用的新版本 |

## 3. 已确认决策

| ID | 决策 | 确认答案 | 直接影响 |
|---|---|---|---|
| D-01 | 不可约结果 | 多人可发起 AI 修改，负责人决定采用哪一个 | 协作围绕候选结果，不围绕代码工具 |
| D-02 | 事实源 | 伏羲数据库与不可变源码/构建包 | 外部代码托管不再是 MVP 依赖 |
| D-03 | 权限边界 | 项目成员可发起，Owner/Admin 可采用或退回 | 项目成员关系是唯一业务权限边界 |
| D-04 | Agent 交接 | 一次性任务码只定位任务，认证沿用用户已接入的伏羲 MCP 会话 | 提示词不出现仓库地址或代码托管凭据 |
| D-05 | 并发策略 | 候选记录基础版本；采用时执行 CAS | 基线变化则标记“已过期”，不自动合并 |
| D-06 | 版本策略 | 候选与正式版本分离；只有采用才改变当前原型 | 上传候选不会影响线上预览 |
| D-07 | 人工决定点 | 采用与退回必须由负责人显式操作 | Agent 不得自行采用或发布 |
| D-08 | MVP 截断 | 只完成单原型候选闭环 | 源码分支、代码审核流和实时协同全部延后 |

## 4. MVP 范围

### 必须有

- 在项目原型上发起修改，得到可复制的一次性任务提示词。
- Agent 兑换任务码并回读当前原型、基础版本与源码下载入口。
- Agent 上传 ZIP 作为候选，平台校验入口并生成独立预览。
- 负责人查看候选、采用或退回；采用生成新正式版本。
- 采用前比较当前版本与基础版本，过期候选不可覆盖新版本。
- 所有关键动作可回读，重复兑换和重复采用失败关闭。

### 明确不做

- 外部代码仓库、分支、合并请求、事件回调、服务账号与源码自动合并。
- 浏览器代码编辑、实时共同编辑、CRDT、通用任务看板。
- 多原型项目 release 和 routeKey 在本纵向切片中不扩展。

## 5. 交互原则

- 一屏一任务，项目预览页只有“让 AI 修改”一个发起主操作。
- 正常路径只说修改、候选、预览、采用和退回。
- 候选上传成功不等于当前版本已更新，必须等待负责人采用。
- 过期状态说明影响与恢复方式：基于最新版重新发起。
- 技术摘要按需展开，默认隐藏 hash、目录和内部状态码。
