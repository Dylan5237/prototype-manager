## 业务事实

伏羲里的“项目”是一个真实平台/产品的原型聚合与轻量协同空间，不是通用项目管理。

示例项目“建模开发平台”包含真实功能菜单：

- 业务域建模
  - 实体建模
  - 方法建模
  - 接口建模
- 权限管理中心

不同节点由不同员工负责；复杂模块可由多人分工。菜单节点同时是：真实产品导航、人员协作边界、原型绑定点。点击叶子菜单节点要显示其绑定原型。

必须维持以下关系：

`伏羲项目 -> 真实产品菜单节点 -> 负责人/成员 + 绑定原型 -> 正式版本/候选版本`

候选上传不能替换正式版本，只有负责人显式采用后才生成新正式版本；基础版本变化时现有过期/CAS 保护不能被绕过。

## 这次只解决一个核心问题

现有页面的平台导航、项目菜单、工具栏、右侧协作、预览边界和 iframe 内部 UI 层层嵌套，导致原型只占一小部分屏幕。请把“项目浏览”和“原型工作”拆成两个模式：

### 项目浏览态

- 继续显示真实产品菜单，因为此时用户在理解项目结构与选择工作范围。
- 显示当前菜单节点的负责人、绑定原型、正式版本、待处理数量和必要协作概览。
- 主操作是“进入原型工作台”。
- 未绑定节点显示真实空状态与现有权限允许的绑定入口。

### 原型工作台态

- 默认以 iframe 原型画布为主，不常驻左右两栏。
- 顶部只保留紧凑上下文：项目、菜单路径、原型、当前版本。
- 保留紧凑工具栏：正式/候选切换、设备宽度、适配宽度、“让 AI 修改”。只展示有真实数据支持的状态。
- “项目菜单”使用左侧覆盖式抽屉。
- “待处理/模块协作”使用右侧覆盖式抽屉。
- 两个抽屉互斥；打开一个时关闭另一个。
- 抽屉覆盖画布而不是改变主体列宽。
- 专注/全屏只是增强；即便不开启，默认画布占比也必须合格。
- 返回项目浏览态时保留当前菜单节点；刷新工作台也要恢复菜单路径和绑定原型。

## 硬性验收

在 1440×900 的桌面窗口、左右抽屉默认关闭时：

1. 原型画布宽度 / 工作区主体宽度必须至少为 0.80。
2. 原型画布高度 / 扣除导航与紧凑工具栏后的可用高度必须至少为 0.75。
3. 平台 shell 必须满足 `scrollWidth <= clientWidth`，不得出现横向滚动。
4. 默认结构不能是“固定左菜单 + 中间画布 + 固定右协作”的三栏。
5. 左右抽屉不能同时打开，且打开时不能让主体重新排版变窄。
6. 不开启专注/全屏时也必须通过上述条件。

功能上还必须验证：

- 切换叶子菜单会显示对应绑定或空状态。
- 进入工作台、刷新、返回项目都能保持当前菜单上下文。
- 正式/候选、AI 修改、采用、退回继续走现有真实数据与权限逻辑。
- 无候选时不显示可操作的伪候选标签。
- 现有候选 Smoke、采用权限、基础版本 CAS 和过期保护未被删除或绕过。
