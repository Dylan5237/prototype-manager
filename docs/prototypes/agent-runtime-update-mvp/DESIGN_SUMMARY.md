# 伏羲 MCP 与 Skill 延后更新设计摘要

> 设计基线：2026-08-21
> 状态：延后更新边界已确认；Windows 本地技术试验已完成；服务端状态与版本回报第一切片已实现

## 1. 结论

已完成首次接入的用户在伏羲点击“安排更新”后，平台只记录更新意图；本地文件不立即改变，AI 客户端下次启动时由稳定启动器先完成 MCP 与 Skill 的校验、切换和 Smoke，再启动 MCP。更新失败保留旧版本，用户仍可继续使用。

## 2. 用户与核心任务

| 项目 | 当前确认答案 |
|---|---|
| 主用户 | 已完成首次接入的伏羲用户 |
| 触发 | 伏羲发现稳定版本高于该设备最近上报版本 |
| 用户动作 | 查看影响，点击“安排下次启动更新” |
| 点击后的事实 | 只产生待更新意图，不立即写本地文件、不唤起脚本 |
| 执行时机 | AI 客户端下一次启动、MCP 进程启动之前 |
| 可观察结果 | 新版 MCP/Skill 可用，原有设备会话和凭据保留 |
| 最高成本失败 | 新版不能启动或 Skill 不可发现，导致 AI 客户端失去伏羲能力 |

## 3. 已确认决策

| ID | 决策 | 确认答案 | 直接影响 |
|---|---|---|---|
| D-01 | 不可约结果 | 已接入用户无需重跑完整接入即可更新本地 MCP/Skill | 更新是独立动作，不复用首次接入提示词 |
| D-02 | 执行时机 | 延后到 AI 客户端下一次启动前执行 | 不做常驻服务、深链接和后台强推 |
| D-03 | 确认语义 | 用户点击只代表“同意下次启动更新” | 页面不能显示“正在更新”或伪造完成 |
| D-04 | 事实源 | 服务端发布清单和更新意图是平台权威；本地安装清单是设备事实 | 启动器必须回读实际版本后才能报完成 |
| D-05 | 组件边界 | MCP 与 Skill 作为兼容发布单元一起切换 | 不允许对外报告半更新成功 |
| D-06 | 失败策略 | staging、摘要/语法/Smoke 失败均保留旧版并回滚 | 旧版继续可启动，用户可稍后重试 |
| D-07 | 凭据策略 | 更新复用既有设备会话；凭据目录与版本目录分离 | 不新增连接码，不把 refresh token 放进页面或制品 |
| D-08 | 首次迁移 | 要支持自动更新，AI 客户端配置最终必须指向稳定启动器 | 旧安装需要一次迁移；新用户从接入时直接安装 |
| D-09 | MVP 截断 | Windows、stable 单渠道、手动确认、下次启动、回滚 | 深链接、常驻守护、多平台、灰度延后 |

原设计中的“一次性 update ticket、`fuxi-agent://` 深链接、浏览器唤起本地更新器、立即更新”标记为 `superseded`，不再作为当前实施依据。

## 4. MVP 范围

### 必须有

- 服务端发布不可变 MCP/Skill 兼容版本清单。
- 伏羲显示“有更新”，用户可查看影响并点击“安排下次启动更新”。
- AI 客户端下次启动前由稳定启动器读取待更新意图，下载/校验制品并原子切换 `current`，保留 `previous`。
- `node --check`、MCP Smoke、Skill 发现检查；任一失败自动恢复旧版。
- 页面分别显示“已安排”“下次启动执行”“更新完成/已恢复旧版”。

### 明确不做

- 不在浏览器中执行 PowerShell、Node 或任意服务端脚本。
- 不要求当前客户端关闭时立即更新，不注册 Windows 自定义协议，不运行常驻后台服务。
- 不新增日常更新连接码或 update ticket；复用已有设备会话。
- 不自动升级 Node.js，不改用户业务目录、MCP 配置和 `FUXI_CREDENTIALS_FILE`。
- 不把静态原型、本地试验或单元测试当作 16077/16088 真实验收。

## 5. 用户提示基线

页面必须直接说明“现在不会发生什么、什么时候发生、失败怎么办”:

1. 有更新：**“更新不会立即修改本地文件；你下次打开 AI 客户端时，伏羲会在 MCP 启动前自动更新。”**
2. 点击后：**“已安排下次启动更新。当前客户端继续可用；请下次重启 AI 客户端以应用新版本。”**
3. 失败时：**“新版本检查未通过，已恢复上一版本。当前客户端仍可继续使用，稍后可重试。”**

## 6. 交互原则

- 先说结果：用户先看到“现在不会更新、下次启动才更新”，再按需展开版本和校验细节。
- “已安排”与“已完成”严格分开；页面不因按钮点击显示成功。
- 当前客户端不被打断；等待启动是正常状态，不显示为异常。
- 失败给出可继续工作的结论和下一步，不要求用户理解目录、脚本或 token。
- 只有“安排下次启动更新”是确认页主操作，重试和查看记录按状态渐进出现。
