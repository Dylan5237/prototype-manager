# 伏羲 MCP 与 Skill 主动更新设计摘要

> 设计基线：2026-08-21
> 状态：方向已确认，MVP 设计完成，代码实现未开始

## 1. 结论

伏羲平台发布新的 MCP stdio 与 Skill 版本后，已接入用户能在平台看到更新、主动确认并通过本地更新器完成安全替换，不必再次让 AI 运行完整接入流程。

## 2. 用户与核心任务

| 项目 | 已确认答案 |
|---|---|
| 主用户 | 已完成首次接入的伏羲用户 |
| 触发 | 伏羲发现用户设备上的 MCP 或 Skill 版本低于平台稳定版本 |
| 核心动作 | 用户在更新通知中点击“更新组件”，确认后启动本地更新器 |
| 可观察结果 | MCP stdio 和 Skill 都显示目标版本，连接测试与 Skill 发现通过，原有会话凭据保留 |
| 最高成本失败 | 更新中断或半替换导致 MCP 无法启动、Skill 丢失或 refresh token 丢失 |

## 3. 已确认决策

| ID | 决策 | 确认答案 | 直接影响 |
|---|---|---|---|
| D-01 | 不可约结果 | 已接入用户无需重复 AI 接入即可完成组件更新 | 更新是独立用户动作，不再复用首次接入提示词 |
| D-02 | 事实源 | 服务端发布清单是版本权威，本地安装清单是设备事实 | UI 不根据缓存猜测成功，必须回读本地与服务端状态 |
| D-03 | 权限边界 | 用户只能更新自己的设备会话，平台管理员发布稳定版本 | 更新票据按用户、设备、版本绑定，不能跨设备复用 |
| D-04 | 人工决定点 | 发现更新自动通知，安装必须用户点击确认 | 不做后台静默覆盖，不打断正在执行的 MCP 调用 |
| D-05 | 安全边界 | 浏览器不能直接执行脚本，由首次接入时安装的本地更新器承接 | 使用 `fuxi-agent://` 深链接，缺失时提供命令行回退 |
| D-06 | 原子性 | MCP 与 Skill 作为一个兼容发布单元更新，失败整体回滚 | 不接受 MCP 新、Skill 旧的未验证半成功状态 |
| D-07 | 更新凭据 | 更新使用短期一次性 update ticket，不把 refresh token 放进 URL | 票据过期或已消费后必须重新从伏羲发起 |
| D-08 | MVP 截断 | 先做稳定渠道、单设备、手动确认、原子替换和回滚 | 多渠道灰度、后台静默更新、跨平台守护进程延后 |

## 4. MVP 范围

### 必须有

- 服务端保存 MCP/Skill 兼容版本、SHA-256、下载地址、最低 Node.js 和 API 版本。
- MCP 启动或刷新会话时上报本地 MCP/Skill 版本；伏羲首页展示“有更新”状态。
- 用户点击更新后生成短期单次 update ticket，通过本地更新器下载并校验两个制品。
- 更新器保留凭据文件和上一版本，执行临时目录安装、原子切换、`node --check`/Skill 发现检查和失败回滚。
- 伏羲页面显示下载、校验、切换、回滚或完成结果，用户能继续使用原有设备会话。

### 明确不做

- 不在浏览器中直接执行 PowerShell、Node 或任意服务器下发脚本；浏览器只启动已安装的本地更新器。
- 不做无人确认的静默更新、跨用户远程推送、任意渠道灰度编排和在线代码编辑。
- 不在更新过程中升级 Node.js、重写用户 MCP 配置或移动 `FUXI_CREDENTIALS_FILE`。

## 5. 交互原则

- 更新通知只说“哪个组件有新版本、为什么值得更新、是否需要重启”。
- 默认主操作只有“更新组件”；版本详情、文件摘要和兼容条件按需展开。
- 更新中明确显示阶段和下一步，不显示“已完成”直到本地回读与连接检查成功。
- 失败保留上一版本，给出“重试”“查看原因”“继续使用旧版本”三个清晰结果。
- 没有本地更新器时，不伪造一键更新，显示一次性安装指引和命令行回退。
