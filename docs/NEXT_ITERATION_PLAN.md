## 1. 迭代结论

下一阶段不设置一个笼统的“持续优化”任务，而是拆成六个有明确退出条件的阶段：

1. 阶段 20：Backlog 与性能基线收口。
2. 阶段 21：本地与远程仓库治理。
3. 阶段 22：伏羲平台项目模块 2.0。
4. 阶段 23：伏羲原型 Skill 质量与效率优化。
5. 阶段 24：MCP、更新、生成与上传性能稳定性优化。
6. 阶段 26：帮助中心与手册维护；帮助中心验收后再进入手册提示词/MCP 动态读取。

阶段按 `20 -> 21 -> 22 -> 23 -> 24` 依赖推进，但性能数据采集从阶段 20 开始，不能等到阶段 24 才建立基线。阶段 22/23 如发生 API、MCP schema、项目任务字段、ZIP、runtime profile 或安装更新契约变化，必须作为跨仓库变更一起设计、验证和绑定 commit。

## 3. 总体实施原则

1. **先事实、后优化**：先记录可重复测量的耗时、体积、成功率和质量结果，再选择优化方案。
2. **轻协作优先**：不以 GitLab 仓库、分支或 MR 作为默认项目协作路径。
3. **两仓分别负责**：平台仓库负责 Web、后端、MCP 和维护者发布 Skill；配套仓库负责用户侧原型规范、runtime profile、生成和交付工作流。
4. **跨仓契约绑定**：两边都改时分别提交、分别验证，并在发布证据中绑定 platform commit 与 Skill commit。
5. **测试不冒充上线**：本地 build/test、16077 测试和 16088 生产验收分别记录。
6. **删除和生产写入单独确认**：清理、远端分支删除、16088 发布和回滚均不得由计划授权替代当次确认。
7. **一个独立任务一个 commit**：避免把 Backlog、项目模块、Skill 和性能改动混入同一提交。

## 7. 阶段 23：伏羲原型 Skill 质量与效率优化

### 7.1 阶段目标

在不破坏 profile、写入门禁和可恢复状态机的前提下，提高首次生成质量、减少无关上下文、降低修复轮次，并强化项目任务到 Skill 交付的连续性。

### 7.2 实施范围

#### A. 黄金样例与质量基线

- 建立固定同题样例，覆盖 `vue3-element-plus`、`vue3-skyui`、静态 HTML。
- 覆盖 `alignment` 和 `implementation-proof` 两种输出模式。
- 保存需求、选用 profile、生成结果、构建记录、截图、质量检查和交付回读。

#### B. 机器可读质量门禁

- 检查入口文件、资源引用、README、runtime profile、ZIP 结构和预览回读。
- 检查双滚动、溢出、遮挡、空白区、不可达操作和缺失状态。
- 检查 implementation-proof 中交互控件是否真实使用目标 runtime 组件。
- 输出 PASS/FAIL/UNVERIFIED 和具体修复项，不只输出主观评分。

#### C. 生成—检查—修复闭环

- 形成“生成 -> 构建 -> 截图 -> 检查 -> 修复 -> 再截图 -> 打包 -> 上传 -> 回读”的固定路径。
- 将失败保存在 run-state checkpoint，可恢复但不得跳过失败阶段。
- 记录首次通过率和平均修复轮次。

#### D. 上下文和能力缓存

- 保持只加载一个 specification 和一个 runtime profile。
- 未选择 SkyUI 时不得读取或安装 SkyUI 专属能力。
- 评估 cache 命中时的读取文件数、准备耗时和 schema 一致性。
- MCP schema 不一致时继续 fail closed，不能为提速绕过门禁。

#### E. 项目任务连续性

- 项目任务提示词携带可安全传递的 project/prototype/version/profile 信息。
- `project-bound-update` 尽量从任务上下文解析准确目标，减少重复询问。
- 目标不唯一、版本不明或 profile 冲突时仍必须停止并请求确认。

- 多 profile、多模式黄金样例集。
- 机器可读质量报告格式和执行器。
- 自动截图/检查/修复回归路径。

## 8. 阶段 24：性能与稳定性优化

### 8.1 阶段目标

依据阶段 20～23 的数据定位瓶颈，只优化影响最大的链路；同时保证权限、摘要、版本 CAS、质量门禁和失败回滚不因提速被削弱。

### 8.2 测量链路

| 链路 | 必须拆分的指标 |
|---|---|
| MCP 接入 | 连接码生成、兑换、配置、首次启动、`tools/list`、`check_connection`、重启后发现 |
| Skill/MCP 更新 | manifest 检查、下载、SHA-256、解压、Smoke、切换、heartbeat、回滚 |
| 原型生成 | 需求解析、profile 选择、代码生成、依赖准备、构建、首次预览、修复轮次 |
| 打包上传 | 项目校验、ZIP 打包、ZIP 校验、上传、服务端解压、版本写入、回读、预览 |
| 质量稳定性 | 首次通过率、缺失资源、预览失败、版本冲突、更新回滚、重复上传和恢复成功率 |

### 8.3 候选优化方向

- MCP ZIP 当前存在整体读入内存的路径；用 1/20/80 MB 样本测量内存峰值和事件循环阻塞，再决定流式上传或 worker 化。
- 后端 ZIP 摘要、解压和文件切换存在同步 I/O；根据耗时和并发影响决定异步化范围。
- Skill/MCP 更新避免重复下载未变化制品，保留摘要验证和原子切换。
- 生成流程复用有效能力缓存和已验证模板，但不能缓存用户、凭证、项目、原型和版本等动态事实。
- 上传失败使用同一幂等键重试同一组参数；参数变化必须生成新键。
- 质量优化优先减少返工，不以删减必要检查换取表面速度。

## 10. 统一发布与验收门禁

8. 只有准备发布 16088 时运行完整构建、MCP 集成、生产基线、备份和业务验收。
